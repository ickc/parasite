    How it builds

    Read, record, derive, render, write; and only what changed.

    The steps

    1. Discover the sources of each collection.
    2. Read each into a pandoc document, with the read filters.
    3. Record it: a small summary of the page (URL, title, dates, category, tags, description, search text, links, citations, its outputs, the media it uses).
    4. Derive what crosses pages from the records alone: listings, categories, tags, the archive, feeds, the sitemap, search, the graph, the site’s copyright years.
    5. Render each page in each of its profiles, and the derived pages. A page’s document is dropped once rendered.
    6. Write: every file through one output tree.

    Pages are read and rendered in a thread pool: most of the work is pandoc, in its own processes.

    Only what changed

    The records are kept in .para/store.sqlite (ignore it in git). A build reads a source again only when its read key changed, and renders a page again only when its render key changed or a file it produced is gone:

    • the site key: the code (the Python modules loaded, the installed packages, para’s own files), pandoc and its data folder, the configuration, and the files the configuration names for every page ([read]‘s --metadata-file and the like, the profiles’ own templates, pandoc-crossref.yaml). Any change here reads everything again;
    • a read key: the site key and the source’s bytes. And a record is used only while the files its read touched are unchanged: its links’ and images’ files (or that they were missing), the media it references and what those reference, its bibliography and style if it cites, a translation’s primary, and the files and folders its text names (a table’s CSV, a gallery’s folder). So a bibliography edit reads again the pages that cite, and a new photo the page whose gallery has it. A filter that reads a file the document does not name can say so with para.deps.touch(path);
    • a render key: the read key, the page’s copyright years, its link to a report and its translations.

    A derived page is rendered again when its document changed. parasite --full ignores the store. A rebuild with nothing changed takes about a third of a second for a site of a hundred pages.

    The output tree

    Every file has one producer: a page, a derived page, a copied folder, a bundle, a medium, a site-wide file. Two producers of one path is an error. A file is written only when its bytes change, so an unchanged page keeps its modification time. Files in the output folder that no step produced (a deleted page’s) are reported, and removed with parasite --prune.

    Copied files ([files] and media) take no extra space when the output is on the same filesystem as the sources: each shares its source’s blocks, as a reflink (copy-on-write, on XFS or Btrfs) or else a hard link. On another filesystem it is a copy. A file is unchanged when it is that same file, or has the same size and modification time, and is then left alone. para.site writes a file by renaming a new one over it, never in place, so it never writes through a hard link into a source; other tools should not edit the output in place either.

    Media

    [media.folders] are copied by reference: only the files the pages use, from their images and links, raw HTML (src, href, data, poster, url(…)), their image, and what those files use in turn (an HTML plot’s scripts, an SVG’s images, a style sheet’s). [files] are copied whole.

    Media in a source itself (a notebook’s outputs) are written next to the page; a PDF image becomes SVG, which a browser can show.

    Search

    With [search] enabled and pandoc-para[search] installed, para.site indexes the records with Pagefind and makes the search page ([search] page). The index is sharded: one more page changes a few of its files. The search box in the navigation sends ?q= to it. Every page is indexed in the site’s language (Pagefind searches the index of the search page’s language only). Tags and categories are its filters, and a page’s tags are searched as its words.

    Links

    With lychee installed, para.site checks the output’s links when the build is done, offline: every link and media reference from the site’s files to its files must resolve, or the build fails (the output is written either way; a build that serves or watches only logs them). This guards the media copied by reference: a reference para.site did not see would be a broken link here. lychee reads the HTML, raw HTML and <style> elements included, but not style attributes or CSS files.

    Links known to be broken are excluded by [check] exclude, regular expressions of URLs (a site’s file is a file:// URL); [check] links = false turns the check off.

    The post graph

    With [graph] enabled and pandoc-para[graph] installed, para.site writes graph.json from the records (links, citations, external links, a page’s other outputs) and the /graph/ page; every page gets a graph of its neighbours.
